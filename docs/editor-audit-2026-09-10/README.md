# 笔记编辑专项检查与优化计划

日期：2026-09-10；源码基线：`bff1973`。

本轮按用户要求删除宽泛的有道功能对比评估，范围收敛到编辑笔记本身。重点是操作是否符合预期、是否改错内容、是否保持光标与选区，而不是增加采集、分享、标签、模板等外围能力。

## 本轮结论

**确认 5 个编辑问题，主要集中在格式处理和选区管理。** 编辑器有对应按钮，并不代表在部分选区、跨段落、混合格式和表格中都能正确工作。应先修这组基础规则，再继续查图片、粘贴、撤销、长文和真机输入。

本轮通过 Codex 内置浏览器操作独立页面，复用生产 `MarkdownEditor` 与 `FormattingToolbar`，实际选中文字、点击按钮并核对写出的 Markdown 和 GFM 渲染。测试样本仅在内存，不连接真实 Vault 或同步服务。此证据覆盖组件交互，不等同于完整应用保存流程或真机验证。

未修改生产编辑逻辑。以下问题仍待修复；9 月 6–7 日已经完成的修复不重复列入。本轮没有拿“缺少某个功能”代替 bug。

## 已复现问题

### E01 · P1：局部取消加粗会误改选区外文字

- 样本：`**甲乙丙丁**`。
- 步骤：仅选中“乙丙”，点击加粗按钮取消格式。
- 实际源码：`甲乙丙丁`。未选中的“甲”和“丁”也失去加粗。
- 期望：只取消“乙丙”的加粗；“甲”和“丁”仍为加粗，例如 `**甲**乙丙**丁**`。
- 影响：长段中修改局部样式会影响周围内容，用户需要额外修复。
- 原因：`markdown-input.ts:169` 的 toggleInlineMark 找到包含选区的节点后，直接移除整个节点的首尾标记，没有拆分选区左右两侧。
- 修复方向：非空选区按范围增删格式；空光标与完整选中分别制定行为。保留选区外原格式、文字和方向。
- 验收：选前半、后半、中间、全部以及反向选区；嵌套粗斜体；一次撤销恢复原文和合理选区。

### E02 · P1：跨段落加粗生成不能正确渲染的 Markdown

- 样本：两段文字，中间有空行。
- 步骤：编辑器中全选，点击加粗。
- 实际源码如下，标准 GFM 渲染中星号直接出现，没有形成两段加粗：

```md
**第一段

第二段**
```

- 期望：每个可格式化段落独立加粗，并保留段落结构，例如 `**第一段**`、空行、`**第二段**`。
- 原因：toggleInlineMark 对整个选区只添加一组首尾标记；没有根据段落、列表、代码等结构分段。
- 修复方向：为跨块选区建立格式化范围；不把空行、列表标记、代码块围栏等当普通正文包裹。不要仅靠正则拆换行，否则容易破坏列表和代码。
- 验收：双段落、三段落、段落+列表、含空行和代码块；核对语义渲染及一次撤销，不只断言字符串多了星号。

### E03 · P2：格式操作后丢选区，连续加格式会插入占位文字

- 样本：`一段文字`。
- 步骤：选中整段，先点加粗，接着点斜体，不重新选中。
- 实际源码：`**一段文字***斜体文字*`。
- 期望：原选中文字继续保持选中，第二个按钮仍作用于它，得到粗斜体；不凭空添加“斜体文字”。
- 原因：加格式分支将选区收成 `from + inserted.length` 的单光标。第二次操作进入无选区占位逻辑。
- 修复方向：有选区操作完成后保留内容选区；空光标插入占位时选中占位正文，便于直接覆盖。统一按钮与快捷键的规则。
- 验收：加粗→斜体、加粗→删除线、格式→链接；不插入无关文案；选区方向、滚动位置和撤销粒度合理。

### E04 · P1：取消双反引号行内代码只去掉一个反引号

- 样本源码：双反引号包裹 `a`、反引号、`b`，即 ```` ``a`b`` ````。
- 步骤：选中代码中的 `a`、反引号、`b`，点击行内代码按钮取消格式。
- 实际源码：```` `a`b` ````。渲染变成 `a` 为代码、后面的 `b` 和尾部反引号另行显示。
- 期望：移除实际的完整分隔符，正文字符保持；如果输出纯文本需要转义，也应保持可见内容不变。
- 原因：toggleInlineMark 固定认为行内代码首尾标记长度为 1。合法代码跨度可使用多个反引号，不能用常量切片。
- 修复方向：读取真实 CodeMark 分隔符；新增行内代码时根据正文最长反引号串选择围栏长度，并处理首尾空格规则。
- 验收：单/双/三反引号围栏、正文含反引号、首尾空格；添加与取消后可见内容一致；撤销恢复原始源码。

### E05 · P1：表格内加粗再加斜体，会把加粗误取消

- 样本：单元格源码 `**加粗文字**`。
- 步骤：点单元格进入编辑，选中“加粗文字”，点击斜体。
- 实际单元格源码：`*加粗文字*`，加粗消失。
- 期望：增加斜体并保留加粗，例如 `***加粗文字***`。
- 原因：`table-edit-target.ts:42` 的 inlineTableFormat 只比较选区左右紧邻的字符；粗体的两个星号被误当作斜体的一对单星号，因此执行了“取消斜体”。检测工具栏状态的函数做了部分排除，但真正执行函数没有同样的语义判断。
- 修复方向：正文和表格共享行内格式语义分析；处理纯文本单元格时仍按 Markdown 语法判断，避免两套启发式规则产生相反结果。
- 已额外检查：本例点击撤销可恢复 `**加粗文字**`，没有据此宣称存在不可恢复的数据丢失。
- 验收：正文/单元格使用同一组样本，粗斜体叠加、删除线嵌套、代码内星号均一致；不新增占位字，不影响别的单元格。
