## 一、用户可见的变化

### A. 即时预览 ⇄ Markdown 源码

格式工具栏多了一个花括号图标（窄屏在「更多操作」菜单里，带分隔线与格式项分开）。点一下进入纯 Markdown 源码：标题标记、表格管道、图片语法都以字面文本显示，预览装饰与表格网格消失，语法高亮与文本编辑照旧。再点一下回到即时预览。

- 模式是**本机编辑偏好**（localStorage），不写进笔记正文、不随笔记同步到远端。
- 与只读锁定、兼容阅读视图互相独立：源码模式只改「怎么看着写」，不改「能不能写」，界面上也没有把语义相近的按钮并成一组。
- 切换不动正文、不重建编辑器（撤销历史保留），并会在切换前把表格单元格/公式块里未提交的局部草稿显式落定。

### B. 附件队列

连续拖入/粘贴多批附件不再「第二批被拒绝」。每一批排进队列，编辑区上方常驻一块队列面板：

- 每个文件有独立状态：等待中 / 写入中 / 已写入 / 失败（带原因）/ 已取消。
- 进度只报「第几个 / 共几个」与每个文件的状态——底层写盘没有字节进度回调，因此**不显示百分比**。
- 等待中的批次可以整体取消；已结束的批次可以「只重试失败的 N 个」（已成功的不重传、正文里也不重复插入）。
- 写入期间切笔记、重命名、切库都不会写错笔记：每批写入都绑定**发起时**的库与编辑会话身份，落笔锚点每次重新取一次。
- **文件写入与正文插入分开记账。** 文件写进去了、引用却没进正文（原笔记被删、已切库）时，面板说的是「已写入 N 个附件，正文引用未插入」而不是「已插入 N 个」，取消也不会把这条失败改写成成功。
- 重试期间按钮显示「正在重试 N 个」且不可再点：连点两次会把同一个文件传两遍、正文里出现两份引用。重试成功后原记录的失败项就地变成「已写入（重试补上）」，重试按钮随之消失。

> 面板顶部把每个文件的当前状态逐条列出；进度计数只在批次含多个文件时显示（单文件时「1 / 1」不携带信息）。

### C. 粘贴图片降级

粘贴中导入不了的图片（`data:`、`file:`、空地址）保留可见占位文字并说明原因，有 `alt` 时保留其说明文字，不再静默消失。剪贴板同时给了真实图片文件时，HTML 那条路只留 `alt`，图片引用交给附件队列，一张图只进一次。未放开任意 `data:`/`file:` URL，协议与路径校验不变；HTTP(S) 外链图片行为保持兼容。

覆盖判定是**逐图**做的：HTML 里有两张导入不了的图、剪贴板只给了一个文件时，只有真能对上的那张不留占位，另一张的占位必须留住（否则它连痕迹都没有了）。能确认的只有两种情形——`src` 文件名与某个剪贴板文件同名，或者导入不了的图片数与图片文件数一一对应（Word / 飞书的典型形态）。对不上就多留一个占位，宁可啰嗦也不静默丢图。

只有当 HTML 转换不出任何文字（整次粘贴只剩图片）时，图片文件也照样入队：转换结果此时是 `null`，若把入队挂在「有非空 Markdown」上，文件和默认粘贴都不会发生，图片连同占位一起消失。

## 三、已实现（代码已落地）

- 源码模式走**两次 `Compartment` 重配置**（`livePreview` 与 `tableEditing` 同时关闭），不卸载组件、不重建 `EditorView`。
- IME 组合期间切换被挂起（就地 return 且不改 `this.settings`），组合结束后落地。
- 切换前 `activeTableEdit(view)?.commit()` + `commitOpenRichEditors(view)` 显式提交局部草稿，绝不静默丢弃。
- 附件任务绑定发起时的 `{cacheId, editorSessionKey}`；重命名（`editorSessionKey` 不变）跟随新路径继续写，切库拒绝写入，原笔记被删则走显式降级并如实告知。
- 锚点失效时回退为「追加到原文末尾」，不改写到当前打开的笔记；已写入的附件一定把引用落进正文。
- **书签的归属笔记在发起时固定，并在 `captureInsertion` 里校验。** 队列执行到某一批时可能已经切走，同步读当前编辑器会捕获「此刻打开的那篇」的身份，连书签自身的守卫也会通过——那是把引用写进别人正文的路径。发起时算好的编辑器会话 key 一路带到 `captureInsertion`，对不上就返回 `null` 走降级。
- **降级落点再次校验库身份。** 写入开始时校验过 `cacheId`，但写入是异步的，落笔时可能已经切库；笔记 ID 里含类型与路径，跨库同名路径并不罕见，只按编辑会话 key 查找会把旧库附件的引用追加进新库里另一篇笔记。

## 五、本轮修掉的真实缺陷

### 5.1 自测阶段发现的两处（新增代码自己引入）

写 e2e 时才暴露：

1. **空剪贴板文件导致图片静默消失。** `图片数 === 文件数` 在「HTML 有图、剪贴板没有任何文件」时是 `0 === 0`，恒真，于是这次粘贴走进「文件会补上引用」的分支——但根本没有文件，图片既没有引用也没有占位，连同刚加的降级占位一起消失。已抽出 `shouldInsertClipboardImageFiles` 并补「至少要给到一个图片文件」这一条。

2. **有文件补引用时仍报「导入失败」。** 剪贴板文件会补上这张图，但 `alt` 为空的图片仍渲染出「（图片无法导入：…）」——图片马上就要出现，这句话是假消息。已改为覆盖场景下无 `alt` 时什么都不留。

### 5.2 代码复评发现的六处（均已复现、已修、已验证）

复评给出 6 项（3 项 P1、3 项 P2），逐条在本机复现后确认成立，全部修复：

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | 队列建批次时才读 `editorRef.current` 取书签 | 甲笔记排第二批、第一批未结束时切到乙 → 第二批引用插进**乙**的正文；书签自身的身份守卫也会通过 | 入队时算好编辑器会话 key 一路带到 `captureInsertion`，对不上返回 `null` 走降级 |
| 2 | 降级落点只按编辑会话 key 查找 | 写入期间切到另一个含同路径笔记的库 → 旧库附件引用追加进新库笔记 | 降级前再校验 `target.cacheId`，不符则记为明确失败并说明 |
| 3 | 文件入队调用写在 `if (markdown)` 内 | HTML 只剩图片时转换结果为 `null` → 文件不入队、默认粘贴照常发生，图片连占位一起消失 | 入队独立于是否产出非空 Markdown，并一并 `preventDefault` |
| 4 | 重试不记录与原批次的关系 | 连点两次重试 → 同一文件传两遍、正文两份引用；失败项永远停在失败、按钮一直可点 | 运行期间锁住重试；重试收尾后按位置回填原失败项 |
| 5 | `imagesCoveredByFiles` 是整次调用的全局布尔值 | 两张导入不了的图 + 一个文件 → 两张的占位一起被删，可只有一张真被补上 | 改逐图判定 `createClipboardImageCoverage`（同名或数目一一对应才算覆盖） |
| 6 | 取消收尾无条件覆盖 `batch.notice` | 原笔记已删除、引用没进正文时，仍报「已写入的附件仍插入了正文」 | 文件写入与正文插入分开记账（`batch.insertion`），取消不覆盖失败原因 |

每条都有单测或 e2e 用例，且用「把修复退回去」验证过会失败（见第四节变异表）。

### 其他已知限制

- 底层写盘不可中断：取消**运行中**的批次只能停止「后续文件」，当前文件会写完并如实标为已写入、引用照插（面板明说这一点，不伪装成整批没发生）。
- 队列支持取消单个等待项，但 UI 只暴露整批取消（`cancelItem` 有服务层用例覆盖，未接面板）。
- 队列状态不需要跨应用重启恢复，本轮未实现。
- 逐图覆盖判定里，「数目一一对应」这一分支是按数量推断的：两张导入不了的图配两个文件时，即使它们其实不是同一对，也会认定都被覆盖。这是为了兼容 Word / 飞书那种 `src` 指向临时目录、按文件名根本对不上的形态；宁可漏留占位，也不让每张图前面多一句假的「导入失败」。
- 重试的进度记录是**独立一条**新批次，原批次只更新失败项状态。面板上因此会同时看到两条记录（原批次的失败项 + 重试批次），这是刻意的：原批次的失败历史不该被抹掉。
- `e2e/editor-link-click.spec.ts` 的 2 条用例（桌面 + 窄屏各 2，共 4）在本轮开始**之前**就已失败：`单元格默认续写，长表格工具条常驻并吸顶` 找不到表格行列菜单的「添加行」按钮，`工具栏整行格式保持选区并支持再次取消` 在 `selectOption("")` 处失败。已在未改动的基线上（`git stash` 后）复现同样 4 项失败，确认与本轮无关，本轮未修。

## 七、手动验收步骤

### A. 源码模式

1. 打开任意含标题、加粗、图片、表格的笔记。
2. 点工具栏花括号按钮（窄屏：更多操作菜单里的「Markdown 源码模式」）。
3. 确认：正文变成字面 Markdown（`# 标题`、`| 列 |`、`![图](路径)`），表格网格与图片控件消失，仍可输入。
4. 再点一次回到即时预览，确认正文一字未变。
5. 刷新页面，确认仍是源码模式（偏好留在本机）。

### B. 附件队列

1. 选一批图片插入，在写入完成前再选一批。
2. 确认队列面板显示两条：一条「正在写入（n / m）」，一条「等待写入」，且**没有**百分比。
3. 等待完成，两条都变成「已插入 N 个附件」，正文里每张图各一条引用。
4. 写入进行中切到另一篇笔记：确认队列面板仍显示原批次且署名原笔记，另一篇笔记正文零改动（复评第 1 项的验收点）。
5. 让某个文件写入失败（例如在大文件写入期间断网）：面板出现「只重试失败的 N 个」，连点两次确认只传一次，成功后该条变成「已写入（重试补上）」且按钮消失（第 4 项）。
6. 写入进行中删掉原笔记：完成后面板说「已被删除，附件已写入但正文引用未插入」，**不会**说「已插入 N 个」，也不会复活那篇笔记（第 6 项）。
7. 写入进行中切换到另一个含同路径笔记的库：确认新库笔记正文零改动，面板提示引用未插入（第 2 项）。

### C. 粘贴降级

1. 从网页复制含图片的富文本粘贴（外链图片）：行为与以前一致。
2. 在 DevTools 里构造一张 `data:` 或 `file:` 图片的粘贴：确认正文出现「图片无法导入：…」的可见文字，有 `alt` 时保留其说明文字。
3. 用系统截图粘贴（剪贴板只有图片文件、无文本）：确认图片正常写入并插入一次，正文里没有第二份原始地址。
4. 在 DevTools 里构造「HTML 里两张无 `alt` 的 `file:` 图 + 剪贴板只给一个图片文件」：确认其中一张的占位仍在正文里，另一张（有文件补上的）不留占位（第 5 项）。
5. 同 4，但 HTML 里只有一张无 `alt` 的图：确认正文**不出现**「图片无法导入」，图片直接由附件队列插入（第 3 项的路径，转换结果为 `null` 时文件仍须入队）。

## 八、验证环境

`e2e` 用例全部使用独立的离线 vault（IndexedDB `swell-note-vault-cache`）与本地附件队列，不连接真实云端、不改动真实笔记。「写入进行中」的时间窗口由 `File.prototype.arrayBuffer` 的可控延迟制造，不用固定延时猜竞态。手动验收请在 `pnpm dev` 起的本地实例上进行。
