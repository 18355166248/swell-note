## 修复前确认问题：P1，Tab 焦点交接期间全选命令会覆盖整篇笔记

复现：进入单元格，⌘A 全选格内文字、输入「甲甲」、Tab 切到下一格，立即再按 ⌘A 并输入「乙乙」，继续 Tab 和录入。期望只修改目标单元格；异常时整篇测试笔记变为最后录入的「丙丙」（前面有空格），表格和前后正文都被覆盖。不是普通的选区显示偏差，也未证明不可撤销。

事件证据见 [focus-events.json](./focus-events.json)：

1. Tab 在 `.cm-md-table-cell-input` 上触发。
2. 原 textarea 卸载并失焦；下一格尚未获得焦点。
3. Meta / a 事件落到非输入元素（active class 为空）。
4. 焦点转到 `.cm-content.cm-lineWrapping`。
5. 后续 input 与 Tab 都作用于正文，最终缓存正文被替换。

源码链路：

- `src/components/editor/markdown-table-widget.ts:1279`：提交先注销目标并移除 textarea。
- `src/components/editor/markdown-table-widget.ts:1078`：下一格焦点经 setTimeout 延迟恢复。
- `src/components/workspace/workspace.tsx:2372`：焦点不在输入控件且没有模态框时，全选快捷键回退到编辑器。
- `src/components/editor/markdown-editor.tsx:1527`：没有活动单元格时，全选作用于整个正文。
- 焦点恢复还会校验正文选区；全选正文已改变选区后，旧恢复不会再抢回焦点。

属于异步时序竞争，不是每次触发。桌面带事件记录的诊断三次中出现两次；整理为带断言的正式复现用例后，三次中出现一次。移动端 Chrome 模拟的组合用例也出现过相同正文覆盖，最终一轮未复现；没有真实移动设备/系统输入法验收。

回归命令（修复前存在概率性失败，修复后要求全部通过）：

```sh
pnpm exec playwright test e2e/table-focus-race.spec.ts --project=desktop-chrome --workers=1 --repeat-each=3
```

修复建议：让表格导航的焦点交接空窗仍被识别为表格编辑上下文，避免页面级全选兜底介入；同时核对快速连续输入和撤销。不能通过测试中额外等待焦点来掩盖问题，也不应直接移除所有页面全选行为。

## 修复实现与验证

键盘 Tab、Enter、方向键导航使用的 `input.table.navigate` 事务的装饰重建改用微任务，在当前 CodeMirror 更新结束后执行；下一格焦点恢复紧随其后，保证下一次用户键盘事件到达前已经有活动单元格。原定时补偿和文档、选区、焦点校验保留，用户已切换到其他输入框时不会抢回焦点。鼠标/触屏点击、菜单操作和普通失焦保存仍使用 `input.table` 和原定时调度，避免在触摸点击完成前移除目标格；其他正文更新的表格装饰调度与页面级全选实现不变。

新增确定性单测只推进微任务、不执行定时器；修复前稳定失败，修复后验证连续 Tab 的目标输入框与活动目标均已就绪。另测焦点转移到外部输入框后不被微任务或定时补偿抢回，以及普通失焦保存不会提前移除尚待点击的目标格。

浏览器测试不在 Tab 后插入等待，保留真实的快速全选和输入顺序。同时覆盖退出表格后正文聚焦、正文失焦两种页面全选路径，确认全选替换正文及撤销恢复整篇笔记仍正常。
