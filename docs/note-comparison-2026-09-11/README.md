# Swell Note 与有道云笔记：笔记能力差距和优化计划

日期：2026-09-11。Swell Note 源码基线：`3c7b5ed`。

## 1. 判断与范围

**Swell Note 已具备日常 Markdown 笔记的主要能力，当前最值得投入的是内容保真、编辑操作效率和跨端连续性。** 不宜用功能按钮数量给出“达到有道的百分之几”：两者定位不同，而且当前没有同平台、同样本的双产品用户测试数据。

本轮聚焦单篇笔记的创建、输入、排版、粘贴、表格、图片、长文查阅、撤销与保存恢复；导出只讨论写完一篇笔记后的交付。采集、AI、团队协作、标签、模板等不进入本期计划，延续上一轮编辑专项的范围。

建议产品方向：**保留标准 Markdown、本地文件和离线编辑的基础，改善无需记语法也能顺畅写作的操作层。** 不为追齐有道普通富文本的字体、颜色、分页和复杂布局而引入私有正文格式。

### 证据边界

- **本轮执行**：读取当前生产源码、近期审计及测试；调用生产 `htmlToMarkdown`，通过 ReactMarkdown 渲染和 DOM 文本断言验证粘贴转换。既有转换测试 18 项通过，新诊断 6 项失败，其中前 5 项是文本保真缺陷，第 6 项是内嵌图片不受支持的能力/反馈缺口。
- **历史记录**：9 月 10–11 日格式、表格、图片及桌面组合流程的验证结果。本轮不把历史测试数字写成重新执行的结果。
- **有道侧**：核对公开官方帮助和 Mac/Windows 更新日志；普通笔记与 Markdown 笔记分开比较。官方页面的版本号是文档所列版本，不代表已安装版本；未核对会员权益和各端完全一致性。
- **未覆盖**：本轮未操作有道私人笔记，未执行双产品实机对照、完整应用粘贴、真实 Word/Excel 剪贴板、iOS/Android 真机和真实云同步。因此不宣称有道在下面五个样本中一定表现正确，也不把未测场景当成确定缺陷。
- 本轮仅整理评估与计划，未修改生产实现。开始时已有的 `src/components/editor/__cand-check.test.ts` 保持不动。

## 3. 本轮确认的问题：富文本粘贴保真

以下五项都由生产转换函数输出、标准 Markdown 渲染和文本断言复现，**仍待修复**。它们是 Swell Note 自身问题，不是有道已通过这些样本的证据。优先级 P1 表示内容正确性问题，应先于新增编辑入口处理；目前没有证据将整个编辑器定为 P0 不可用。

| ID | 输入与预期 | 当前实际结果 | 原因与修复要求 |
| --- | --- | --- | --- |
| N01 · P1 | HTML 普通段落中的 `请原样输入 **关键词** 和 [说明](地址)`，应保留字面量 | 写入相同字符却被 Markdown 解释为粗体和链接，阅读变成“请原样输入 关键词 和 说明” | 文本节点直接透传。按上下文转义源文本，区分源文本与转换器生成的语法标记，不能最后对整段 Markdown 统一转义 |
| N02 · P1 | 链接标签“数组[0]”应完整保留且仍可点 | 输出 `[数组0](https://example.com)`，方括号被删除 | 链接标签用正则删除方括号。改为合法序列化/转义，保留可见标签与链接目标 |
| N03 · P1 | `Hello<strong> world </strong>again` 应显示 `Hello world again` | 输出 `Hello**world**again`，显示 `Helloworldagain` | 格式包装先 trim 内容，吞掉两侧有意义空格。空格移到格式标记外，保持浏览器可见文本 |
| N04 · P1 | 行内代码包含 `a`、两个反引号、`b`，应全作为代码显示 | 固定用双反引号包装，正文中的双反引号提前闭合代码，显示文本也发生变化 | 围栏长度应大于正文最长连续反引号串，处理首尾空白；尽量与已有行内格式命令共享规则 |
| N05 · P1 | PRE 内容为三行：`before`、四个反引号、`after`，应保留完整代码 | 外围也用四反引号，中间行提前结束代码块；`after` 变成正文，另出现空代码块 | 当前只在三/四反引号间二选一。根据正文选足够长围栏，保证内部空行及尾部内容保留 |

## 5. 优化实施计划

以下为一名熟悉项目的开发者的**粗估净人日**，含定向回归，不含设备准备、外部服务等待及新增复杂问题；不是发布日期承诺。先完成第一批再用测量结果重估后三批。

| 批次 | 顺序与任务 | 预计投入 | 交付及退出条件 |
| --- | --- | --- | --- |
| A：内容保真 | 第一优先，修 N01–N05；给不支持的粘贴图片保留占位/说明；补清晰的纯文本粘贴入口；真实剪贴板与现有格式/表格回归 | 3–5 人日，估算信心中 | 五个诊断转绿；可见文本、代码结构和链接不变；一次粘贴可撤销；不扩大到选区外；代码块内粘贴按字面内容处理；对不支持内容有反馈 |
| B：基础编辑效率 | A 稳定后：补有序列表、清除语义格式；建立共享编辑命令，再接 `/` 菜单和桌面选区格式栏；H4–H6 二级入口 | 4–6 人日，估算信心中 | 同一命令在工具栏/快捷键/菜单和表格允许的上下文中语义一致；菜单不抢选区/输入法；代码块、URL、表格内不误唤起 `/`；每次命令一次撤销 |
| C：长文和编辑连续性 | B 的共享命令基础上加整块选择/复制/移动/转换；补可见代码折叠；验证图片占位及长文性能；真机输入专项 | 4–7 人日，估算信心低 | 移动一个完整列表/代码块不拆坏结构；大纲/查找命中折叠区能定位；切阅读/笔记后合理恢复光标和滚动；真机候选词及选区流程通过 |
| D：保存恢复与单篇交付 | 修 L03 生命周期及库级结果反馈；明确本地历史边界、增加版本差异预览/恢复为副本；单篇 Markdown+附件包，随后打印/PDF | 4–7 人日，估算信心低 | 原笔记删除后不复活、不误写其他笔记，失败可见；恢复前保留当前内容；笔记附件包在空目录离线可打开；打印/PDF 不含工具栏，长表/代码不被横向裁掉 |

完整队列粗估 15–25 净人日。第一期只承诺 A+B 的范围（约 7–11 净人日），C/D 依据反馈和实机结果滚动安排。已知可能影响内容归属的 L03 应先补复现；如复现证明会误写/丢引用而非仅遗留附件，则提前到 A，不等 D。

### 每批具体约束

- **A 的主要入口**：`html-to-markdown.ts`、`markdown-editor.tsx`、`markdown-input.ts`。抽取可复用的围栏/转义规则，但保留“HTML 原文转 Markdown”和“编辑现有 Markdown”两种输入语义。不要直接把整套格式编辑器套进转换器。
- **B 的命令定义**：每条命令定义可执行条件、作用范围、选区结果、一次撤销；清除格式保留文字与链接目标，先明确它是否移除链接，不将该决定藏在实现里。表格内不可用的块命令应明确禁用。
- **C 的性能目标**：在同一设备/构建/样本下记录基线与 P95；建议普通文档输入到绘制 P95 ≤50ms、100k 字符混合长文 P95 ≤100ms，作为首轮拟定门槛，测量后校准。它们是计划目标，不是已有实测性能。
- **D 的附件包边界**：仅打包该篇引用的 Vault 内附件；外链保留原链接并列明，避免未经选择下载全部网络资源；缺失附件出清单。复用整库备份的路径校验能力，不把整库内容作为单篇导出。
- **队列和历史**：运行中任务绑定稳定笔记身份并接受重命名映射；文件写完后再改正文，失败保留可恢复状态；历史要明确仅本机、上限及保留方式，不把它当远端备份承诺。

### 每批共同验收门槛

1. 文本不丢、不重、不改选区外内容，正文/表格/阅读态保持语义一致。
2. 快捷键、按钮与菜单执行同一操作；一次用户命令可以撤销和重做。
3. 异步完成不抢走正在输入的焦点，不写到另一篇笔记。
