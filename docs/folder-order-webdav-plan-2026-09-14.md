# 文件夹排序接入 WebDAV：方案与 Kimi 实现任务书

评估日期：2026-09-14。代码基线：`63ef486`。本文件是设计交付，不代表功能已实现或已在坚果云真机验证。

## 推荐决策

每个 WebDAV 笔记库在根目录下保存一个 `.swell/folder-order.json`，设备保留本地工作副本。拖动立即生效，上传遵循现有手动/自动同步设置；另一台设备在同步、启动恢复连接或回到前台时读取配置。使用 ETag 条件写入防止并发覆盖，排序冲突由用户选择整份本机或云端顺序。

第一期只同步顶层文件夹顺序。保留已通过评审的拖动、子树整体跟随、根目录固定、键盘、触摸和只读本地排序行为。

| 方案 | 收益 | 代价 | 结论 |
| --- | --- | --- | --- |
| 独立 JSON 文件＋条件写入 | 普通 WebDAV 文件操作，容易检查、备份和测试 | 需要配置工作副本、冲突状态 | 推荐 |
| WebDAV 自定义属性 PROPPATCH | 无额外文件 | 要新增属性协议和兼容验证，现有代码无此基础 | 本期不选 |
| 每设备事件日志或排序 CRDT | 可以尝试合并多个设备的排序意图 | 排序语义、日志清理、目录改名均更复杂 | 本期不选 |
| 时间戳决定整份覆盖 | 实现较少 | 设备时钟不可靠，而且会静默丢弃另一端意图 | 不采用 |

## 适用范围：先确认两个客户端的打开方式

主方案适用于电脑和手机都通过 WebDAV 打开同一远端根目录。云端身份由远端位置决定，不依赖两个设备 localStorage 中的库名一致。

如果电脑用“打开本地文件夹”，手机用 WebDAV，即使它们看起来是同一批笔记，也不能自动把两个库绑定起来。本期 WebDAV 接入本身不会让电脑本地排序上传：本地适配器仍为本机排序，UI 应明确这一点。

混合方式需要额外一期：本地适配器读写同一 `.swell/folder-order.json`，由用户明确配置的网盘客户端同步该文件；验证本地目录与远端映射、隐藏文件是否同步、文件监听、原子替换及网盘冲突副本。单纯把本地 JSON 写入目录不具备 WebDAV ETag 的并发保护，不能宣称两种通道并发编辑已安全合并。本期不根据同名目录自动关联，也不借用当前 WebDAV 凭据上传其他本地库。

## 用户可见行为

1. 在电脑拖动排序：本地立即更新，并显示“文件夹排序待同步”。默认手动模式点击现有同步按钮上传；后台/重连自动同步模式沿用原设置。
2. 手机点击同步：即使手机没有任何待上传笔记，也拉取排序；成功后立即更新列表并保存到本机。
3. 手机重启页面、恢复已配置的 WebDAV adapter，或应用从后台回到前台：只读拉取配置。前台事件按库合并并建议间隔至少 30 秒；显式同步跳过该限流。没有凭据或离线就保留本地显示，不弹出反复登录框。
4. 不承诺实时推送。手机一直停留在前台且没有任何同步事件时，不会即时感知另一台电脑的修改；本期不新增轮询。
5. 本地有未上传修改时，拉取不能直接覆盖；两端都改过则显示“文件夹排序存在冲突”，提供“使用云端顺序”“使用本机顺序”和关闭后稍后处理。
6. 排序失败不阻止笔记阅读、拖动及无关笔记同步。总结果显示部分失败；不能输出“云端与本机一致”。

## 远端文件协议

文件位置：`<WebDAV root>/.swell/folder-order.json`。例如 root 为 `/Swell`，配置是 `/Swell/.swell/folder-order.json`。

```json
{
  "schemaVersion": 1,
  "changeId": "随机 UUID，每个新的待提交快照生成一次",
  "order": ["工作", "学习", "生活"]
}
```

- 只包含相对笔记库根目录的顶层目录标识；复用当前顶层 path 表示，不能写设备绝对路径、库名、账号、密码或笔记正文。
- 系统“根目录”不写入 order，始终由 UI 固定。没有自定义顺序时 `order: []` 是有效值；不借此创建空白远端文件，除非是明确重置/编辑的结果。
- `changeId` 用于确认上传结果不明时是否已经成功；不是版本排序依据，不按 UUID 大小决定胜负。同一次上传重试复用同一个 changeId。
- ETag 只存本地同步状态，不写进 JSON。语义比较以顺序内容为准，不因 changeId 不同制造内容冲突。
- 校验 schemaVersion、类型、路径和大小；建议正文上限 256 KiB、最多 5000 项、单项最多 1024 个字符，读取实际字节也要有限制，不能只信 Content-Length。拒绝绝对路径、路径分隔符、`.`/`..` 和 NUL，不能拿收到的 order 去执行文件读写。去重必须稳定。
- 同一 schemaVersion 的未知字段应保留后再写回，或明确返回不支持；不能悄悄丢掉。未知新 schemaVersion、非法 JSON、超限内容：保留本机状态，配置只读报错，不自动覆盖远端。
- WebDAV 扫描已经跳过点开头目录；本地 browser/tauri 扫描和目录监听也应排除 `.swell`，避免配置目录出现在树里或触发无意义重扫。

## 本地工作副本与首次迁移

推荐在现有 IndexedDB settings store 增加独立记录，键为 `folder-order-sync:v1:<cacheId>`；为其提供专用读写函数。该记录是同步状态的事实来源，不能和 v1 localStorage 各自维护可写主状态，也不要依赖 App 的整库笔记快照防抖保存。

记录至少表达：

- 当前 `localOrder`、每次本地意图变化递增的 `localGeneration`。
- `base`：上次已知远端状态，包括 exists/order/etag/changeId；null 表示还没观察过远端，与确认文件不存在不同。
- 未上传意图及来源（旧版迁移候选或升级后用户主动编辑）。
- pending upload 快照的 order/changeId/generation，用于断网、重启和结果不明恢复。
- conflict/error 状态，冲突时保留本机与云端候选，不能清空本机意图。
- 一次性迁移标记，必要时保留旧排序备份，避免每次启动把旧值重新标成待上传。

具体 TypeScript 类型由实现方保持简洁，但应区分 `clean / pending / syncing / conflict / error` 和远端缺失/尚未读过的状态。每库的状态转换和持久化串行化；卸载或切库不取消已经成功确认的数据落盘，但不能更新新库的 UI。

迁移规则：

| 首次观察结果 | 行为 |
| --- | --- |
| 只有 v1 历史排序，云端已存在有效配置 | 云端优先，旧本机值保留备份；不把历史本地值当作刚刚发生的新修改上传 |
| 只有 v1 历史排序，确认云端文件不存在 | 作为待上传迁移候选；只有进入允许写入的同步流程时才条件创建 |
| 没有旧排序，云端存在 | 拉取并应用，保持 clean |
| 没有旧排序，云端不存在 | 正常使用自然顺序，不创建空文件 |
| 首次读取前用户主动重新排序，云端存在且不同 | 保留用户最新顺序，进入首次并发选择；不能套用“历史排序云端优先” |

初始化读 IndexedDB 期间用户若已拖动，迟到的 hydration 不得覆盖新代次。localStorage v1 只作为一次性输入，不自动遍历上传其他缓存库。存储不可用时当前会话仍可排序，但提示“本机保存失败”，不能声称刷新后仍安全保留。

## 同步判定和并发处理

采用 base/local/remote 三方判定，比较合法配置的完整 order。它是冲突检测，不是把排序数组交给 Markdown 行合并器。

| 条件 | 处理 |
| --- | --- |
| 无本地未上传意图 | 采用远端并更新 base |
| local 与 remote 顺序相同 | 更新 base/ETag；确认相应代次已同步，不重复 PUT |
| 本地改变、remote 与 base 顺序相同 | 用刚读取的远端 ETag 条件上传本机快照 |
| 本地与远端相对 base 都变了且不同 | 保留 local，存 remote 候选，进入 conflict，不自动覆盖 |
| base 未知 | 按首次迁移规则，不能假装已有共同基线 |
| 曾经存在的远端配置被删除 | 视为远端重置；本地 clean 则恢复自然顺序并记录缺失基线，本地有不同改动则冲突；不得重新迁移旧 v1 值复活配置 |

远端缺失与 `order: []` 可在“排序内容”比较时等价，但存在性仍决定用条件创建还是条件更新。发现配置 404 时要确保本次连接/检查确认了笔记库根目录存在；根目录本身丢失或请求身份错误不能当作配置重置。

冲突选择行为：

- 使用云端：重新读取云端，以用户操作时捕获的库和本地代次校验后应用。用户选择期间若又拖动，不得把新本地编辑无提示丢掉。
- 使用本机：重新读取云端，把用户明确选择的当前本机候选以最新 ETag 条件写入；若再次 412，保留冲突，不能无限自动覆盖后来版本。
- 关闭提示：保留冲突，不影响笔记操作；不要自动重试制造循环弹窗。

## HTTP 规则与失败处理

条件创建用 `PUT + If-None-Match: *`，更新用 `PUT + If-Match: <strong ETag>`。HTTP 标准要求 If-Match 使用强比较，不能把弱 ETag 去掉 `W/` 冒充强 ETag，也不能退回无条件 PUT。[RFC 9110 §13.1.1–13.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)

新增专用 JSON 接口，复用现有 webDavFetch 的代理/原生传输、认证与错误处理：

- `GET` 读取 JSON 和 ETag，`Content-Type` 写入为 `application/json; charset=utf-8`。首期文件很小，默认完整 GET 足够，不强制实现 304 缓存优化；避免陈旧 HTTP 缓存。
- 404 是缺失，不是空 JSON；401、403、412、429、网络错误须能区分，不通过中文错误字符串匹配状态。
- 首次真正写入时才 `MKCOL .swell`；沿用目录存在处理，确认不是同名普通文件。不在每次只读刷新创建目录。
- 412 后最多进行一次读回与重新判定，不把旧快照直接换新 ETag 强写。重试次数有界；无变化错误不能改变自动队列签名。
- PUT 返回新强 ETag 时可以记录已确认结果。若没有 ETag，应 GET 读回并核对 changeId/order，绝不能沿用旧 ETag 表示新的远端版本。现有 Markdown 更新函数的旧 ETag fallback 不可直接照搬到新协议。
- PUT 超时/网络断开可能已在服务端成功。保存 attempted 快照，下一次先 GET：远端 changeId 和 order 匹配，则确认该次结果；不同则重新三方判定，不盲目重复覆盖。
- 如果读回的新远端已被其他设备再次修改，保留实际读回版本和未确认意图，按三方规则处理，不把“PUT 曾成功”误当作“当前远端等于本机”。
- 无强 ETag 的服务端可以读取配置，但本期不更新既存配置；标记服务端不支持安全更新，保留 pending。不用 Last-Modified 或 If-Match:* 替代版本比较。
- 元数据失败不阻断无关笔记同步。认证失效仍复用统一凭据失效处理，不额外暴露密码。

## 库身份、代次与取消：必须保留的边界

每次请求捕获 `{cacheId, adapter, syncRunToken, localGeneration, uploadSnapshot}`。所有 await 后处理必须核对运行是否取消、库是否仍匹配、该操作是否仍有效。

- A 库请求切到 B 后完成：允许安全记账到 A 的独立工作副本，不能调用仅面向当前库的顺序 setter，也不能改 B 的 pending/error/同步时间或列表。UI 更新通过按库订阅派生。
- 上传代次 g 时用户又拖动成 g+1：g 成功只更新 base 为已上传快照，保留 g+1 的 localOrder，并继续 pending。不能把当前顺序改回 g 或一次性清空 dirty。
- 拉取等待期间用户又改动：用最新 localOrder/generation 重新判定，不能覆盖。
- 已上传但取消/切库导致 UI 不再接收结果：下次可通过 attempted changeId 与 GET 恢复，不能假装服务器已回滚。
- 刷新/重连/自动同步/前台只读拉取使用同一个按库串行协调器；先解决 `refreshVault` 无 adapter 分支和 `connectWebDav` 的防重入口，不另外制造一条并发写链。
- 不要求阻止用户拖动，不修改已经通过评审的 `FolderSortDndContext`。如果远端配置在拖动期间到达，应暂缓可见顺序替换，或明确取消该次拖动；不允许指针下的列表突然换序而把错误顺序再提交。

## 目录发现、新增、重命名与删除

远端扫描当前有目录/文件数量上限，并且空目录枚举能力有限。未显示的目录不一定已删除，排序文件不能成为目录存在性的事实来源。

- 显示时，已有目录按顺序排列，未记录的新目录追加，根目录固定，子树整体跟随。
- 不因本机未扫描到某条 order 就自动从云端删除它。远端列表不得被 `visibleFolders` 的子集整体覆盖。
- 本地拖动可见顶层集合时，只替换配置中这些可见成员所在的槽位，保留不可见成员的相对位置，新增成员追加。例如配置 `[A, X, B]`，本机只见 `[A,B]`，拖成 `[B,A]` 后完整配置为 `[B,X,A]`。
- 已确认的目录重命名在发起库迁移排序路径，保持位置；删除只清理确认删除的路径。由用户目录操作产生的变更属于本地配置意图，需要同步，不能标成远端已确认。
- WebDAV 重命名/删除当前是笔记工作副本的 MOVE/DELETE 队列。发布新目录名相关排序前，必须保证相关结构操作已成功；保守方案是在本库仍有失败/冲突的结构操作时暂停排序上传并说明原因，普通正文失败不必阻断排序。
- 拉取不能把本地未同步的重命名路径改回远端旧路径。没有可靠目录映射时保留本机并进入冲突，首期不实现跨设备目录 UUID 系统。

## 现有同步流程的接入顺序

一次完整同步建议：

```text
捕获库身份和运行令牌
  → 读取远端排序配置（独立收集配置错误）
  → 现有目录、附件、笔记同步
  → 刷新目录/笔记列表
  → 按最新本地代次三方判定排序
  → 条件上传或应用远端排序
  → 分别落盘结果，汇总成功/冲突/部分失败
```

远端读取到上传之间仍可能发生并发，最终必须由条件 PUT 防护。排序阶段不能仅挂到“有待上传笔记”的分支。重连 `connectWebDav`、无 adapter 的刷新和已有 adapter 的刷新都应走同一协调能力。

还需接入：

- `pendingSyncCount`：一份排序配置算一个待处理项目，不按目录条目计数；error 的待上传项和 conflict 分开展示。
- `autoSyncQueueKey`：内容/代次变化才改变签名；自动失败后遵循现有有限尝试规则。只读拉取不产生待上传项。
- `retryFailedSync`：只有排序失败、没有 failedNoteIds 时也能重试。笔记单项重试不顺带上传无关配置；排序提供独立重试路径或完整同步入口。
- 同步日志、结果提示和 `lastSyncedAt`：`loadVault` 目前会提前更新时间。需让整轮完成状态包含排序结果，未解决冲突/失败不能让整体看起来全部同步成功；前台只读配置检查不冒充整个库已同步。
- 缓存删除/隐私清理：同步元数据与其 cacheId 一并清理；正常重建搜索索引不得丢掉未上传排序。不得在凭据配置中存排序。
